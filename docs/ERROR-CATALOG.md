# PipDock — Error Catalog

*Version 0.1 · 2026-07-17. Single source of truth: `crates/pipdock-core/src/errors/catalog.rs`. Every user-visible failure carries exactly one code; classifiers run over engine stderr in priority order (first match wins), falling back to `PD-ENG-999`.*

## 1. Code space

`PD-<AREA>-<NNN>` — areas: `ENV` environment, `ENG` engine, `RES` resolution, `BLD` build, `PKG` package/index, `NET` network, `PRM` permissions, `SNP` snapshot, `SYS` system, `HLT` health, `INT` internal.

`Code::ALL` holds **35** codes; this table has **32** rows because PD-HLT-001..004 share one. `every_variant_is_listed_in_all` and `every_documented_code_has_exactly_one_variant` in `errors/catalog.rs` pin both numbers.

Classifier hygiene: patterns live beside unit tests with captured real stderr fixtures (collected in spike SP-2 and grown from bug reports); a fixture must exist for every code before it ships — or the code is listed, with the module that raises it, in the `internally_raised` table of `tests/classifier_corpus.rs`, which PD-ENG-004 joined in 1.4.0. **Every WinError needle includes its closing bracket**: Python prints `[WinError N]`, and the bare `winerror 5` also matched 50, 53 and 59, so `[WinError 53] The network path was not found` came out as PD-PRM-001, "use a venv". The corpus runs over `pip/`, `uv/` (uv 0.13's `error:`/`cause:` rendering) and the frozen `uv-0.11/` (miette's `×`/`╰─▶`), and `both_uv_renderings_classify_identically` pins that the two renderings classify alike. Classifying correctly was not enough: `classifier_corpus.rs` passed while uv's adapter never asked the classifier at all (DATA-FLOW §7), so `plan_parsers.rs`'s `every_failed_capture_reaches_the_user_as_the_code_it_was_captured_for` asks the function each resolve actually returns through.

## 3. Presentation rules

GUI: `code · localized one-liner · [Details ⌄ stderr tail ≤ 40 lines] · [Copy full log] · [Report bug]`. CLI: `error[PD-XXX-NNN]: <message>` on stderr, the stderr tail beneath it when there is one, and for an internal error (exit 10) `log: <path>` — the day's `pipdock-cli.<date>.log`. Under `--json` the error envelope is the command's one document on stdout: `{code, message, stderrTail}`, with `stderrTail` null when there is none. **There is no `reason` field**, though this line named one until 1.4.0: `message` is the core's developer-facing detail, in English, because the CLI is English-only (I18N §1), and the GUI receives the same three fields (`WireError`) and looks its one-liner up from `code`. Localization: only the one-liner and action text are localized; codes, messages and stderr never are.

## 4. Bug-report pipeline (owner requirement: console error attached to template)

1. The GUI keeps a ring buffer (last 64 KB, `LOG_RING_BUFFER_BYTES`) of engine stdout/stderr, cleared when a plan begins. It holds engine output only: PipDock's own log (`data\logs\`, new in 1.4.0) is not in it and not in the URL — Settings' Logs row copies that log's tail on its own (`logs_tail`).
2. **Report bug** builds a prefilled GitHub new-issue URL against `.github/ISSUE_TEMPLATE/bug_report.yml`:
   `https://github.com/poli0981/pipdock/issues/new?template=bug_report.yml&pd-version=…&os=…&engine=…&python=…&error-code=…&log-excerpt=…`
   Given the environment, `python` carries the engine's version too (`Python 3.12.4 · pip 26.2.1`); the GUI asks for it only when the user clicks, which costs a subprocess (U31).
3. URL budget: GitHub rejects very long URLs, so `log-excerpt` is cut, tail-biased, until its **percent-encoded** form fits 6 000 characters (`BUG_REPORT_EXCERPT_CHARS`). The cap was applied before encoding until 1.4.0, and encoding decides what GitHub sees — an accented letter costs up to nine bytes, a path separator three — so a log full of Vietnamese paths built a ~20 KB link and GitHub answered with an error page instead of the form (M51). The full log is not lost: the error row's *Copy full log* puts the whole ring on the clipboard (`BugReportLink.log`), and hides itself when there is nothing to copy.
4. Nothing is ever sent automatically — the user reviews the issue form in their browser. This is the entire "telemetry" story, and the row says so beside the button rather than leaving the user to guess what "Report bug" does.

Built in `pipdock_core::report` and called by both heads, so `pipdock self report-bug` and the GUI's `report_bug_url` cannot drift apart the day the template gains a field. The GUI's ring buffer is fed from **three** places, not one: the progress forwarder — which every streaming command shares, so health- and audit-progress lines land there as well as plan-progress — and `plan_resolve`'s success *and* failure paths: a resolve emits no progress events at all, and a plan that would not resolve is the commonest thing anyone reports. The CLI has no ring, so its excerpt is empty and the URL simply omits the parameter. 1.4.0 gave it a log file (`pipdock-cli.<date>.log`), but `self report-bug` does not read it yet.
